### ✅ Готово и в проде

- **FastAPI + PostgreSQL**, миграции (включая подтверждение почты),
  полный цикл регистрация → подтверждение → вход (JWT), полный CRUD

  `tests/test_polygons.py`.
- **Реальная ML-модель подключена** (`app/services/ml_bridge.py`, мост к

  на baseline при любой проблеме с ML-окружением — сервис не падает.

  `HttpVegetationDataService.findPolygonsInRegion` шлёт `region` ровно в

  закрывает пункт из критериев «автопоиск контуров при выборе региона».
- **Авторизация фронта решена** — `HttpVegetationDataService` реально
  шлёт `Authorization: Bearer <token>` (`tokenProvider` от
  `AuthRepository`), так что `POST /polygons/custom`/`DELETE

## GEE: как получить доступ (для того, у кого американский/не-РФ аккаунт)

У аккаунта из России Earth Engine регистрацию не пропускает — авторизация
молча зацикливается обратно на выбор аккаунта Google (это ограничение на
стороне Google, не баг у нас). Нужен кто-то с аккаунтом, не привязанным к
России (биллинг-регион/страна аккаунта).

**Шаги (займут ~10 минут):**

1. Зайти на https://code.earthengine.google.com/register под нужным
   аккаунтом → выбрать **«Unpaid usage»** (некоммерческое использование —
   бесплатно, без карты, с квотами, которых с запасом хватит на демо).
2. В процессе регистрации Google предложит **создать новый Google Cloud
   проект** — можно прямо там же, отдельно ничего готовить не нужно.
   Earth Engine API включится в этом проекте автоматически как часть
   регистрации.
3. Установить `earthengine-api` (Python) и запустить обычную (личную)
   авторизацию, чтобы проверить, что всё работает:
   ```bash
   pip install earthengine-api
   earthengine authenticate
   ```
   Откроется браузер → авторизовать → готово. Это создаёт **личные**
   учётные данные (на своей машине) — для сервера они не подходят.
4. **Для сервера/бэкенда нужен Service Account** (личный OAuth не переживёт
   передачу на другую машину и не годится для Docker):
   - Google Cloud Console → тот же проект → **IAM & Admin → Service
     Accounts** → Create Service Account (любое имя, например
     `kosmohack-gee`).
   - Зарегистрировать этот service account в Earth Engine отдельно:
     https://signup.earthengine.google.com/#!/service_accounts — вставить
     email вида `kosmohack-gee@<project-id>.iam.gserviceaccount.com`.
   - Создать JSON-ключ для этого service account (Service Accounts → тот
     аккаунт → Keys → Add Key → JSON) — скачается файл, например
     `gee-service-account.json`.
5. Передать (не через git!) `<project-id>` и JSON-файл ключа тому, кто
   деплоит бэкенд. На сервере это ляжет как переменные окружения в
   `backend/ml/.env` (шаблон уже есть в `backend/ml/.env.example`):
   ```
   EARTHENGINE_PROJECT=<project-id>
   GEE_SERVICE_ACCOUNT=kosmohack-gee@<project-id>.iam.gserviceaccount.com
   GOOGLE_APPLICATION_CREDENTIALS=/absolute/path/to/gee-service-account.json
   ```
6. Проверить одним запросом (не требует поднятого веб-сервиса):
   ```bash
   cd backend/ml
   python scripts/check_gee.py --project "$EARTHENGINE_PROJECT"
   ```
   Успех — короткий реальный ответ по тестовому полигону из четырёх
   источников (Sentinel-2/Landsat/MODIS/ERA5).

## Что реализовать на бэке, когда GEE-доступ появится

1. **Поднять `backend/ml/webapp`** как часть бэкенда — либо отдельным
   сервисом в `docker-compose.yml` (проще всего: `uvicorn webapp.main:app`
   в своём контейнере, порт наружу не светить, только для внутреннего
   вызова), либо примонтировать его роуты (`/analyze`, `/find-polygons`)
   как `APIRouter` прямо в `backend/app/main.py` — второе чище, но требует
   свести `webapp/main.py`'s Pydantic-схемы с уже существующими в
   `app/schemas/`.
2. **`GET /polygons`** (`backend/app/api/routes/polygons.py`) сейчас **не
   принимает вообще никаких query-параметров** — ни `region`, ни bbox,
   отдаёт всю таблицу целиком. Flutter-клиент уже шлёт bbox
   (`findPolygonsInRegion` в `vegetation_data_service.dart`) — этот
   контракт нужно наконец реализовать по-настоящему: принять
   `min_lat/min_lon/max_lat/max_lon`, отфильтровать по существующим
   полигонам в БД, и если внутри области ничего нет — вызвать
   `/find-polygons` (после п.1) для реального автопоиска через ESA
   WorldCover вместо текущей фикции (см. `mock_...` на фронте, который
   выдумывает 1-2 прямоугольника).
3. **Живой анализ нарисованного пользователем полигона**: при
   `POST /polygons/custom` (реальные координаты, не anon_polygon_id) —
   вызывать `/analyze` (после п.1) вместо/в дополнение к обычному ORM-flow,
   чтобы `GET /timeseries/{id}` для таких полигонов отдавал восстановленный
   по спутнику ряд, а не пустоту.
4. **README в корне репозитория и `infra/README.md`** — устарели, всё ещё
   пишут «бэкенда ещё нет» / описывают только мок-фронтенд, хотя бэкенд
   полностью готов и задеплоен на `https://skytime.daniel.crazedns.ru`.
   Переписать с реальным способом запуска (frontend+backend+db одной
   командой) — иначе жюри увидит фейковые данные вместо настоящих.

## 0. Открытый вопрос — решить в первую очередь

`anon_polygon_id` в `train_dataset.csv` / `private_features.csv`
**анонимны**. Непонятно, как это соотносится с требованием «пользователь
выбирает регион и полигон на карте, сервис сам получает спутниковые данные».
Скорее всего это два разных потока, и решение должно поддерживать оба:

- **Интерактивный веб-флоу**: пользователь тычет в карту / рисует полигон
  → бэкенд на лету тянет Sentinel-2/Landsat/MODIS + ERA5 через GEE, считает
  NDVI и Z-score. Координаты реальные, `anon_polygon_id` тут ни при чём.
- **Технический batch-инференс** (для авто-проверки): вход — уже готовый
  `private_features.csv` с анонимными id и признаками, без каких-либо
  координат вообще.

Если это верно — фиксируем и не тратим время на попытки «раскрыть»
анонимные id. Если не так — уточнить у экспертов (см. предыдущее
обсуждение вопросов эксперту).

## 1. Данные соревнования

`train_dataset.csv` уже есть в репозитории —
[`../data/train_dataset.csv`](../data/train_dataset.csv)
(получен от организаторов 2026-09-04, положил как есть). `private_features.csv`
всё ещё не найден — искать на платформе хакатона.

**Реальная схема колонок** (не выдуманная — проверено кодом на самом файле):

```
anon_polygon_id, date, s2_ndvi, s2_evi, s2_ndwi, landsat_ndvi, landsat_evi,
landsat_ndwi, modis_ndvi, modis_evi, era5_temp_c, era5_precip_mm, year,
primary_ndvi, doy, ndvi_climatology_mean, ndvi_climatology_std, ndvi_zscore,
n_reference_years, status, crop_type
```

Важные факты, которые в PDF явно не были написаны:

- **99 955 строк, 39 уникальных `anon_polygon_id`** (вида `AOI-0002` …
  `AOI-0077`, нумерация с пропусками — видимо в `private_features.csv`
  часть id из того же диапазона).
- **Даты — с 2010-04-01 по 2024-10-30**, шаг ряда для каждого полигона —
  **календарный день внутри вегетационного сезона** (не «раз в спутниковый
  пролёт»): у одного полигона подряд идут даты с разницей в 1 день, и один
  раз в год — разрыв ~153–154 дня (не-сезон, зима/межсезонье просто
  отсутствует в ряду, а не заполнена пропусками).
- **`primary_ndvi` пуст в ~69.5% строк (69 435 из 99 955)** — это и есть
  «пропуски» на восстановление. `is_synthetic_gap` **в train-файле такой
  колонки нет вообще** — судя по всему, это чисто тестовый служебный
  признак, а в train пропуск = просто нет ни одного спутникового
  наблюдения на этот день ни у одного из трёх сенсоров. Уточнить у
  организаторов, будет ли колонка `is_synthetic_gap` называться так же в
  `private_features.csv`, раз в train её нет.
- **`primary_ndvi` = значение того сенсора, который в этот день реально
  снял сцену**, без усреднения: если есть и `s2_ndvi`, и `landsat_ndvi` —
  `primary_ndvi` берёт `s2_ndvi` (Sentinel-2 в приоритете), иначе следующий
  доступный. Если ни один сенсор не снял — `primary_ndvi` пуст. Это и есть
  «гармонизация нескольких сенсоров», которую нужно повторить для
  `private_features.csv`/своего пайплайна.
- **`status`/`ndvi_zscore` в train уже посчитаны организаторами** и **точно
  совпадают** с порогами, которые уже зашиты во Flutter
  (`Штатное развитие` / `Угнетение биомассы` / `Критическая аномалия`,
  Z≥−1 / −2≤Z<−1 / Z<−2) — свериться, ML-часть не обязана пересчитывать
  формулу, значения уже есть как reference.
- **Культуры — на русском, реальные**: `озимая пшеница` (52 787 строк),
  `зерновые` (27 119), `подсолнечник` (15 975), `пастбища/зерновые` (4 074).
  Это степная зона (южная Россия), не международные кейсы — **демо-регионы
  во Flutter-моке (Меконг/Калифорния/Рондония) не соответствуют реальным
  данным**, стоит решить, менять ли демо-сценарий Flutter под реальные
  культуры/регион, когда появятся координаты.
- `n_reference_years` = 15 у всех просмотренных строк — климатология
  считается по 15 годам истории.

## 2. Задача 1 — восстановление `primary_ndvi` (авто-проверка)

- Для строк с `is_synthetic_gap=True` предсказать `primary_ndvi`.
- Простейший baseline: среднее ближайшего известного значения до и после
  пропуска. Более сильные варианты: линейная/сплайн-интерполяция,
  Savitzky-Golay, Whittaker smoother, модели временных рядов, ML.
- Обязательно маскировать облачность/тени перед расчётом ряда — иначе
  ложные аномалии (частая причина провала на защите).
- **Формат `submission.csv`** (только строки `is_synthetic_gap=True`):
  ```
  anon_polygon_id,date,primary_ndvi_pred
  AOI-0001,2025-06-14,0.543218
  AOI-0037,2025-07-03,0.391005
  ```
  `date` в `YYYY-MM-DD`, разделитель — запятая, кодировка UTF-8, без NaN и
  дублей пар `anon_polygon_id+date`.
- **Метрика**: `RMSE = sqrt(mean((y_true - y_pred)^2))`, переводится в
  `GapScore = round(30 * max(0, 1 - RMSE/0.10), 2)`. RMSE=0 → 30 баллов,
  RMSE≥0.10 → 0 баллов. Порог 0.10 ≈ качество baseline «среднее двух
  соседей».

## 3. Задача 2 — детекция и интерпретация аномалий

Z-score относительно климатической нормы (среднее/std по дню года за
прошлые годы):

```
Z = (NDVI_факт − NDVI_climatology_mean) / NDVI_climatology_std
```

Пороги — **зафиксированы во Flutter-части, менять только синхронно**
(`../frontend/lib/models/ndvi_point.dart`, `ndviStatusForZ`):

| Z | Статус |
|---|---|
| Z ≥ −1 | Штатное развитие |
| −2 ≤ Z < −1 | Угнетение биомассы |
| Z < −2 | Критическая аномалия |

Дополнительно (не обязательно, но усиливает решение): сопоставлять сигнал
с ERA5 (температура/осадки) и соседними датами, чтобы отделять погодный
стресс от выбросов/облаков/смены агрофазы — это должно попадать в поле
`explanation` ответа.

## 4. API-контракт, который уже ждёт Flutter-клиент

**Обновление:** реализация появилась и смёржена в `main`
(FastAPI + PostgreSQL, `backend/app/`) — поля ответов сделаны один в один
под Flutter-модели (см. докстринги в `backend/app/schemas/*.py`, там прямо
процитированы `frontend/lib/models/*.dart`). Расхождения с тем, что уже
реализует Flutter, ниже.

**Реально прогнал интеграцию** (`docker compose up`, миграции, загрузка
`data/train_dataset.csv`, Flutter собран с `--dart-define=API_BASE_URL=...`
против живого бэкенда) и нашёл/поправил два бага:

- **Бэкенд не запускался вообще.** `backend/app/schemas/timeseries.py`:
  поле `date: date` при `from datetime import date` — классическая
  Pydantic v2 ошибка (имя поля совпадает с именем типа), крашила старт
  приложения (`PydanticUserError: ... field name clashing with a type
  annotation`). Поправил на `import datetime` + `datetime.date` в обоих
  местах (`NdviPointOut`, `NdviObservationIn`).
- **Климатология реально бывает `null` в ответе** (`climatology_mean`/
  `climatology_std` — замаскированы для строк-пропусков, ровно как в
  `train_dataset.csv`), а Flutter-модель `NdviPoint.fromJson` делала
  нестрахуемый `as num` и падала бы на ~70% реальных точек. Сделал поля
  опциональными во Flutter (`frontend/lib/models/ndvi_point.dart`) — при
  отсутствии климатологии точка считается «без данных» (не аномальной),
  а не крашит рендер.

После этого весь сценарий (39 реальных полигонов, реальные временные
ряды, реальные аномалии с ERA5-объяснениями) отработал в браузере без
ошибок.

**⚠️ Авторизация — расхождение с согласованным контрактом.**
`POST /polygons/custom` и `DELETE /polygons/{id}` теперь требуют JWT
(`Depends(get_current_user)`, см. `backend/app/api/routes/polygons.py`).
В `docs/tz.pdf` и в исходном контракте, который уже реализует
`HttpVegetationDataService`, авторизации не было — сам backend/README.md
называет её «учебным расширением», не частью задачи. Пока
`HttpVegetationDataService` не шлёт `Authorization`, поэтому рисование и
удаление полигона против реального бэкенда сейчас вернут 401/403.
Решить одним из двух способов (обсудить с бэкенд-разработчиком, не решать
только с фронта):
- Backend: убрать `Depends(get_current_user)` с этих двух роутов, оставить
  auth опциональной/выключенной для хакатон-версии — проще всего.
- Frontend: реализовать прозрачную анонимную регистрацию/логин при
  старте приложения и слать `Authorization: Bearer <token>` — больше
  работы ради фичи, которой не было в ТЗ.

**Реализовано:** параметр `region` у `GET /polygons` (bbox `lat1,lon1,lat2,lon2`
или название региона) — см. `app/services/region_search.py`. Сначала
отдаются уже известные полигоны, чей центроид попадает в область; если
таких нет — сервис сам находит открытые сельхозконтуры через Overpass API
(OSM: `landuse=farmland/orchard/vineyard/meadow`), сохраняет их как
`is_custom=false` и возвращает. Название региона геокодируется в bbox
через Nominatim (OSM). Полноценный ESA WorldCereal не подключён — это
растровая классификация через GEE/STAC, а не готовые векторные контуры,
и требует отдельной инфраструктуры/доступов.

**Разница в схеме:** `PolygonOut.area_id` у бэкенда всегда `null`
(поле для демо-группировки, не часть их модели `Polygon`) — Flutter это
переживает нормально (поле опциональное).

Реализован в `../frontend/lib/data/vegetation_data_service.dart` (интерфейс)
и `../frontend/lib/data/http_vegetation_data_service.dart` (HTTP-клиент,
сейчас не подключён — включается флагом
`--dart-define=API_BASE_URL=http://host:port` в `../frontend/lib/main.dart`).
Точная форма JSON — в `fromJson`/`toJson` моделей (в
`../frontend/lib/models/`: `ndvi_point.dart`, `ndvi_polygon.dart`,
`anomaly.dart`).

> **Из критериев оценки** (`../docs/criteria.pdf`, раздел «Управление
> полигонами», 5 баллов): нужно уметь не только добавлять полигоны, но и
> **удалять** их из набора, и **автоматически находить доступные
> сельхозконтуры при выборе нового региона** (не только по клику
> пользователя на готовый пин/рисование). Ниже — `DELETE /polygons/{id}`
> и параметр поиска по региону у `GET /polygons`. **Flutter-клиент уже
> вызывает оба** (на моках — см. `frontend.md`), на бэкенде их пока нет.

### `GET /polygons?region={free-text или bbox}`
Список полигонов для отображения на карте (открытые контуры
OSM/ESA WorldCereal или уже сохранённые пользовательские).
`region` — опциональный параметр поиска (bbox `lat1,lon1,lat2,lon2` или
название региона) — по нему сервис должен сам подтягивать доступные
контуры из открытых источников для этой территории, не только отдавать
статический список.
```json
[
  {
    "anon_polygon_id": "AOI-0001",
    "label": "Необязательно, для demo-подписи",
    "crop_type": "rice",
    "area_id": "необязательно, для группировки",
    "is_custom": false,
    "points": [[10.02, 105.77], [10.02, 105.79], [10.04, 105.79], [10.04, 105.77]]
  }
]
```

### `POST /polygons/custom`
Пользователь нарисовал свой контур на карте.
```json
// запрос
{ "points": [[10.02, 105.77], [10.02, 105.79], [10.04, 105.79]] }
// ответ — тот же формат объекта полигона, что и в /polygons, с "is_custom": true
```

### `DELETE /polygons/{id}`
Удаление полигона из набора пользователя (204/200, без тела). Только для
`is_custom: true` — открытые контуры OSM/ESA WorldCereal не удаляются,
только скрываются на фронте.

### `GET /timeseries/{anon_polygon_id}`
Ряд NDVI по полигону — **обязательно с разделением исходных и
восстановленных значений** (Flutter отдельно рисует сплошные точки vs
полые кольца):
```json
[
  {
    "date": "2025-06-14",
    "primary_ndvi": 0.62,           // null, если это пропуск (natural gap ИЛИ is_synthetic_gap)
    "primary_ndvi_pred": 0.60,      // восстановленное/предсказанное значение; используется на графике, если primary_ndvi == null
    "is_synthetic_gap": false,
    "climatology_mean": 0.58,
    "climatology_std": 0.06,
    "crop_type": "rice"
  }
]
```

### `GET /anomalies?polygon_id={id}`
Уже сгруппированные периоды аномалий (не по точке, а по непрерывному
отрезку Z<−1):
```json
[
  {
    "id": "AOI-0001-2025-06-14",
    "anon_polygon_id": "AOI-0001",
    "start_date": "2025-06-14",
    "end_date": "2025-09-01",
    "severity": "critical",          // "suppression" | "critical" — см. пороги выше
    "min_z_score": -2.4,
    "deviation": -0.31,
    "explanation": "Свободный текст-интерпретация причины"
  }
]
```

Раньше в контракте был ещё `/tiles/{z}/{x}/{y}.png` (NDVI-растровые тайлы)
— **убрал**, в официальном ТЗ такого требования нет, карта сейчас рисует
полигоны цветом по статусу, а не растровый оверлей. Если решите всё же
делать растровые тайлы — это доп. фича, не обязательная.

Для локального/демо-развёртывания за одним портом (веб-сервис + API) есть
стартовый Caddy-конфиг — [`../infra/README.md`](../infra/README.md).

## 5. Отдельно от веб-сервиса: technical batch-инференс

Спецификация явно требует **вторую, независимую точку входа**: скрипт/CLI,
который принимает `private_features.csv` и на выходе кладёт `submission.csv`
(см. формат в п.2) — без веб-интерфейса, для автоматической проверки на
платформе. Не завязывать это на поднятый веб-сервис.

## 6. Требования к репозиторию (для итоговой сдачи, не только для демо)

- Полный исходный код: подготовка/загрузка данных, предобработка, обучение,
  инференс, модуль детекции аномалий, конфиги — без разрозненных файлов и
  ручного переноса кода.
- `README.md`: назначение, установка зависимостей, источники и структура
  данных, команды сбора/предобработки, команда обучения, команда
  batch-инференса и где появляется `submission.csv`, способ запуска
  веб-демо.
- Зафиксировать версии зависимостей (`requirements.txt` /
  `pyproject.toml`+lock / `environment.yml` / Dockerfile). Предпочтительно —
  Dockerfile/docker-compose на весь стек.
- Если есть обученные веса/скейлеры/сохранённая климатология — либо в
  репо, либо по внешней ссылке в README, подключение без ручных правок.
- Исследовательский отчёт (свободная форма): протокол оценки, EDA, что
  проверяли и что сработало/нет, обоснование финальной конфигурации,
  ограничения.

Из критериев оценки (`../docs/criteria.pdf`, раздел «Качество кода и
документация», 8 баллов) — конкретно, а не «хорошо бы»:

- **Комментарии в коде — на русском языке.** Помогают понимать сложные
  участки, архитектуру, бизнес-логику; не должны быть пустыми/избыточными.
  Пишите сразу по-русски, не переводите потом.
- Корневой `README.md` непустой, оценивается по **факту воспроизводимости**
  — максимальный балл только если решение запускается по инструкции без
  дополнительных правок. Проверить весь путь (frontend+backend+infra) перед
  сдачей, а не полагаться на то, что «и так понятно».
